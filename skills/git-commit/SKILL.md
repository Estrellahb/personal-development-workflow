# 提交规范

> 本文件为项目开发工作流的阶段 07 规范。智能体在测试通过后执行本规范，提交前检查未通过严禁提交。

---

## 一、阶段定位与准入门禁

1. 准入门禁：阶段 06 的测试命令退出码为 0，失败清单为空。
2. 提交前检查构成硬门禁：格式化器与静态检查器未通过时提交必须被拒绝，严禁使用 `--no-verify` 或等效参数绕过。工具缺失或未配置属于阶段 02 的选型缺陷，必须回到阶段 02 修正选型并在 `docs/decisions-architecture.md` 登记，不得在提交阶段绕过或降级。

---

## 二、提交信息结构

格式为 `<type>(<scope>): <subject>`。

| type | 用途 |
| :--- | :--- |
| feat | 新增功能 |
| fix | 缺陷修复 |
| refactor | 不改变外部行为的重构 |
| perf | 性能优化 |
| test | 仅测试相关 |
| docs | 仅文档 |
| build | 构建或依赖变更 |
| ci | 流水线配置 |
| chore | 杂项维护 |
| style | 仅格式调整 |
| revert | 回滚既有提交 |

1. scope 取受影响的模块或阶段目录名，例如 `feat(auth)`、`docs(ui-ux)`。
2. subject 用祈使句、不加句号、不超过 50 字；中文可用，type 与 scope 保持英文。
3. 正文解释"为什么改"，不重复 diff 已经表达的"改了什么"；破坏性变更写入 `BREAKING CHANGE:` footer。

---

## 三、原子性判据

一个提交对应一个可独立回滚的决策。判据：假设单独 revert 该提交，若会破坏另一件不相关的事，则不原子，必须继续拆分。

1. 实现与其对应测试放在同一提交，避免出现引用尚不存在符号的中间态。
2. 不同关注点的改动不得混提：结构调整、引用纠偏、文案修订分别提交。
3. 首次接入格式化器导致的整文件重排，单独以 `style:` 提交一次，不混入功能提交。

---

## 四、提交前自动检查

提交前必须依序通过以下三层，任一失败即中止提交：

1. 格式化器（formatter）：统一空行、缩进、引号、行宽与尾随逗号，只保证一致，不判断对错。常见实现为 Prettier、gofmt、ruff format、rustfmt。
2. 静态检查器（linter）：检查未使用变量、隐式类型、危险写法与规则违规。常见实现为 ESLint、ruff check、golangci-lint、clippy。
3. 提交前钩子（pre-commit hook）：在 `git commit` 前自动执行上述两项，仅检查暂存文件以避免全量扫描拖慢提交。常见实现为 Husky、lefthook、pre-commit 框架。暂存文件中不含目标语言文件时，前两层按不适用处理，钩子必须显式输出 N/A，不得静默跳过。

具体工具与命令由阶段 02 的栈选型确定并写入项目配置文件；本规范只约束"必须挂载并通过"，不指定实现。

---

## 五、阶段完成标准与流转

满足以下全部条件即视为完成本阶段：
1. 提交信息符合上述结构，type 与 scope 取值合法。
2. 单个提交满足原子性判据，可独立回滚。
3. 提交前钩子已实际执行并通过，无绕过记录。
4. 提交仅包含本次意图内的文件，无生成物、缓存、密钥与本地配置。

达成上述条件后，智能体输出提交摘要（哈希、type、scope、变更范围），任务闭环。

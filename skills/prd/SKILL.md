# 产品需求文档撰写规范

> 本文件为项目开发工作流的阶段 03 规范。智能体在完成需求质询与架构分析后必须执行本规范，用于沉淀无歧义、高密度、可指导开发的 PRD 文档。

---

## 一、阶段定位与文档撰写核心原则

1. 准入门禁：阶段 01 确立的最小可行性产品边界与阶段 02 产出的架构选型方案均已获确认。
2. 彻底拒绝黑话与过度包装：坚决杜绝赋能、抓手、闭环、打通心智等空洞的互联网黑话，严禁大段空泛的商业吹捧与防御性废话套话。
3. 工程师人话沟通：秉持朴素、自然、高信息密度的工程师语言风格，像写设备操作手册一样精准描述系统行为。
4. 真实可落地导向：文档直接面向后续的 UI 设计、接口定义、测试编写与工程编码，每一个功能点必须具体到谁在什么前置条件下、执行了什么操作、系统产生什么状态流转、最终得到什么明确反馈。

---

## 二、说人话 PRD 标准骨架结构

智能体撰写 PRD 文档时，必须统一收敛为以下紧凑务实的结构模块：

### 1. 一句话产品定义与交付目标
- 开门见山用一两句大白话讲清楚：这个系统是干什么的、给谁用的、本次迭代要交付的核心价值是什么。
- 严禁铺垫冗长的宏观市场分析与虚无的远景构想。

### 2. 用户核心角色与核心使用场景
- 明确系统当前涉及的真实用户角色，杜绝抽象概括。
- 用最通俗的故事形式描述核心场景：某个角色在遇到什么具体问题时，打开什么界面，完成了什么操作，达到了什么目的。

### 3. 功能模块详细行为规范
每一个功能点均拆解为具体的行为清单，坚决杜绝模糊表述：
- 前置触发条件：用户处于什么状态或拥有什么权限才能发起。
- 输入要素：需要用户填写的具体字段、上传的文件类型与大小限制。
- 业务处理逻辑：系统背后的校验规则、状态变更与核心计算流程。
- 明确输出与界面反馈：操作成功或失败后，界面呈现的提示文案、跳转动作或数据变更。

### 4. 边界防御与明确非目标
- 边界约束：明确定义输入长度极限、数值范围、分页限制与默认排序规则。
- 明确非目标清单：清晰列出本次迭代坚决不做的衍生特性与高级功能，严防需求在实现过程中悄然蔓延。

### 5. 可验证的验收标准对照表
- 每一条验收标准必须是可观测、可执行、非黑即白的确定性事实。
- 严禁出现响应迅速、体验良好、界面美观等主观定性词汇，必须转化为在什么测试数据下、产生什么预期结果的具体测试步骤。

---

## 三、PRD 文档交付路径与命名管理

智能体撰写完毕的 PRD 必须规范持久化到工程目录中：
1. 存储路径：统一存放在项目 docs 目录下的 prd 子目录中。
2. 文件命名规范：采用英文短横线命名法，以业务主题为核心，例如 docs/prd/user-auth.md 或 docs/prd/task-management.md。
3. 版本可追踪性：文档顶部简要注明对应阶段 01 的决策结论与阶段 02 采纳的架构方案，保证研发全链路有据可循。

---

## 四、阶段完成标准与流转

满足以下全部条件即视为完成本阶段：
1. 语言通俗严谨，全程贯彻工程师人话风格，无任何互联网黑话与套话。
2. 功能模块输入、处理规则与输出结果描述精准，边界与非目标界定分明。
3. 验收标准完全客观化与表格化，可直接无缝转换为测试用例。
4. PRD 文档已落盘至指定路径并获得用户确认。

达成上述条件后，智能体输出 PRD 摘要，正式流转至阶段 04 UI 与 UX 设计。

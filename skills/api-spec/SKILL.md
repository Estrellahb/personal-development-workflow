# 前后端接口契约规范

> 本文件为项目开发工作流的阶段 05 规范。智能体在 PRD 与界面设计确认后必须执行本规范，编写代码前必须先确立前后端通信协议与数据结构契约。

---

## 一、阶段定位与契约先行原则

1. 准入门禁：阶段 03 的 PRD 功能清单与阶段 04 的 DESIGN.md 均已确立；无界面项目以 DESIGN.md 的 `界面范围: 无` 声明替代原型。
2. 契约先行原则：严禁在未定义接口契约前直接编写前后端业务交互代码；必须优先确立数据模型与接口协议，前后端以此为基准并行开发。
3. 协议基线与特化支持：全项目默认通信基于标准 HTTP 协议与 RESTful API 风格设计；针对大模型流式输出采用服务端事件发送机制，针对双向实时通信采用套接字协议，针对文件读写采用多段表单或二进制流，特殊通信方式必须在契约中显式声明。

---

## 二、RESTful 资源路径与请求方法规范

接口设计以面向资源为第一准则，兼顾工程实际场景：

### 1. 路径命名规范
- 名词复数与全小写：资源路径优先使用名词复数，小写单词之间使用短横线分隔。
- 特殊场景放宽：允许健康检查、单例系统配置或确有必要的业务操作型接口采用直观语义路径。
- 规范层级嵌套：表达所属关系时使用斜杠层级，例如特定用户的任务列表组织为 /api/v1/users/123/tasks。
- 明确版本控制：前后端交互路径前缀统一声明版本号，例如 /api/v1。

### 2. 标准 HTTP 动词语义映射
- GET：安全且幂等的只读操作，从服务器拉取资源，严禁产生持久化副作用。
- POST：用于新建资源、提交数据或触发服务端计算任务；默认非幂等，针对交易支付或高频任务创建等防重场景，必须设计幂等键防重机制。幂等键通过请求头 `Idempotency-Key` 传递（UUID v4），同一键重复提交返回首次结果；契约中该头对防重端点声明为必填。
- PUT：幂等的资源全量替换操作，客户端提供完整数据覆盖既有记录。
- PATCH：资源局部更新操作，仅提交需变更字段；普通字段覆盖赋值应设计为幂等，涉及累加计数或队列投递等非幂等更新必须明确并发控制与重试策略。
- DELETE：幂等的资源移除操作，从服务器物理或逻辑删除目标资源。幂等指重复调用后资源状态一致，不要求每次返回相同状态码（首次 204、重复 404 属正常）。

## 三、统一数据载荷、字段 Schema 与响应封装

确保全站数据结构在机器解析与人类理解层面具备双重确定性：

### 1. 统一成功响应结构与特殊状态码
- 遵循 HTTP 标准响应体规则：HTTP 204 无内容状态码严禁携带任何响应体；文件流与长文本传输采用专属媒体类型响应。
- 具备响应体的业务接口统一封装格式：
  - code：业务状态码，成功固定标识为零。
  - message：简短的成功描述信息。
  - data：真实的业务返回数据载荷，无返回数据时为 null 或空数组，严禁省略该键。
  - 列表类 data 统一为 { items, page, pageSize, total }，禁止各端点自定义分页字段名。
  - timestamp：服务器响应时间戳，毫秒级整数。

### 2. 统一错误响应结构与安全防线
- 错误封套结构：code（非零业务错误识别码）、message（面向用户的安全提示文案）、errors（字段级校验错误详情数组，元素为 { field, reason }）、timestamp（毫秒级服务器时间戳）。
- 敏感信息阻断红线：面向用户的错误文案严禁泄露底层代码堆栈、数据库语句、内部绝对路径或密钥等敏感数据；内部异常统一通过请求追踪标识关联服务端日志。

### 3. HTTP 状态码精准映射
- 200 OK：请求成功并返回预期数据。
- 201 Created：新资源创建成功。
- 204 No Content：请求成功执行且无须返回响应体，通常用于删除操作。
- 400 Bad Request：请求参数存在语法错误或缺少必填基础字段。
- 401 Unauthorized：未提供身份凭证或登录已失效。
- 403 Forbidden：已认证身份但缺乏目标资源的操作权限。
- 404 Not Found：请求的路由端点或特定实体不存在。
- 405 Method Not Allowed：路由存在但请求方法不被支持；未匹配任何路由仍返回 404，二者不得混用。
- 409 Conflict：由于资源当前状态发生冲突导致请求失败，常用于状态机冲突或重复创建唯一键。
- 422 Unprocessable Content：请求参数格式正确但在业务语义校验层面未通过。
- 429 Too Many Requests：客户端调用超出频次限额，触发限流保护。
- 500 Internal Server Error：服务端未捕获的运行时异常。
- 503 Service Unavailable：服务过载或处于临时维护降级状态。

### 4. 字段规范与查询契约
- 命名与时间规范：JSON 字段命名全站统一采用驼峰命名法，查询参数同样采用驼峰命名（page、pageSize、sortBy、sortOrder）。业务日期字段（如 dueDate、publishedAt）采用 ISO 8601 带时区字符串；响应封套与日志中的 timestamp 按第三节第 1 项使用毫秒级整数，两类不得混用。
- 分页与过滤约定：列表接口统一使用 page 与 pageSize 作为分页参数，排序使用 sortBy 与 sortOrder，并对 pageSize 设定最大上限保护。

## 四、机器可读契约交付物与自动化验证

接口契约必须同时服务于自动化工具链与开发者：

### 1. 机器可读标准契约文件
- 唯一真实可信源：智能体必须在目标项目根目录生成 docs/api/openapi.yaml 规范文件，采用 OpenAPI 3.0 及以上标准。
- 完备性要求：每个端点必须具备唯一的操作标识符、详细的请求参数约束、精准的请求与响应 Schema 定义、错误模型以及身份认证鉴权机制描述。

### 2. 人类友好文档与调试示例
- 辅助业务文档：在 docs/api 目录下按业务模块编写辅助 Markdown 文档，解释核心业务场景逻辑与状态变迁。
- 调试命令样例：每个端点必须提供基于可配置基础路径与占位测试凭证的 curl 调试命令样例，便于结合模拟服务器或真实环境进行调试核验。

---

## 五、阶段机器可验证完成标准

本阶段严禁依赖智能体主观臆断宣布完成，必须逐一满足以下七项确定性验收门禁：

1. OpenAPI 结构与语法校验无报错。优先执行工具级校验，任一可用即可：`npx @redocly/cli lint docs/api/openapi.yaml`、`python3 -m openapi_spec_validator docs/api/openapi.yaml`。两者均不可用时，允许以 JSON 兼容的 YAML 写法并通过 `python3 -m json.tool` 解析，但必须在契约报告中登记"未做工具级语义校验"，并逐条核对本阶段第 2~5 项。
2. 所有端点均具有唯一的 operationId，且请求参数与所有返回状态码均具备明确的 Schema 定义。
3. 前后端通信共用目标项目根目录下的 docs/api/openapi.yaml 唯一定义，无冲突矛盾的派生字段。
4. 认证拦截方式、错误码体系与分页查询约定已在契约中完整声明。
5. 关键核心接口均已提供标准的请求载荷与响应样例数据。
6. 已完成接口清单与 PRD 业务功能及前端设计原型的逐一映射比对，无功能遗漏。
7. 生成的 OpenAPI 契约已落盘，核心数据结构已获得用户明确确认。

达成上述条件后，智能体输出契约检查报告，正式流转至阶段 06 测试规范。

# 前后端接口契约规范

> 本文件为项目开发工作流的阶段 05 规范。智能体在 PRD 与界面设计确认后必须执行本规范，编写代码前必须先确立前后端通信协议与数据结构契约。

---

## 一、阶段定位与契约先行原则

1. 准入门禁：阶段 03 的 PRD 功能清单与阶段 04 的页面设计原型均已确立。
2. 契约先行原则：严禁在未定义接口契约前直接编写前后端业务交互逻辑；必须先确立接口定义并沉淀文档，前后端方可并行开发。
3. 纯粹 RESTful 架构：全项目通信一律基于标准 HTTP 协议与 RESTful API 风格设计，利用标准方法与状态码表达语义。

---

## 二、RESTful 资源路径与请求方法规范

接口设计必须面向资源，遵循以下标准化语义准则：

### 1. 路径命名规范
- 名词复数与全小写：资源路径一律使用名词复数形式，单词全小写，多个单词使用短横线连接。
- 严禁动词入路径：严禁在请求路径中包含类似 get、create、update 或 delete 等动词。
- 规范层级嵌套：表达从属关系时使用斜杠层级，例如特定用户的任务列表路径应组织为 /api/v1/users/123/tasks。
- 明确版本控制：所有对外部署与前后端交互路径，前缀统一包含主版本号标识，例如 /api/v1。

### 2. 标准 HTTP 动词映射
- GET：安全且幂等的资源读取操作，从服务器拉取单个资源或列表，严禁产生副作用。
- POST：非幂等的资源新建操作，用于在服务器创建全新的子资源。
- PUT：幂等的资源全量替换更新操作，客户端提交完整对象覆盖既有记录。
- PATCH：幂等的资源局部微调操作，仅提交需变更的局部字段。
- DELETE：幂等的资源移除操作，从服务器物理或逻辑删除目标资源。

## 三、统一数据载荷与响应封装

全站前后端交互数据一律采用 JSON 格式编码传输，响应结构高度统一：

### 1. 统一成功响应结构
每一个成功的 HTTP 响应均返回统一标准数据体：
- code：业务状态码，成功通常固定标识为 0。
- message：简短的成功描述信息，面向开发人员排查。
- data：真实的业务返回数据载荷，无返回数据时统一为 null 或空数组，严禁省略该键。
- timestamp：服务器响应时间戳，毫秒级整数。

### 2. 统一错误响应结构
发生业务校验失败或服务端异常时，除返回对应级别的 HTTP 状态码外，响应体保持一致：
- code：具体且唯一的非零业务错误标识码。
- message：通俗易懂的错误原因说明，可直接用于前端界面弹窗或就地提示。
- data：详细的字段级校验失败明细列表，无补充细节时为 null。
- timestamp：发生错误时的服务器时间戳。

### 3. HTTP 状态码黄金准则
- 200 OK：请求成功处理并返回预期数据。
- 201 Created：新资源成功创建完毕。
- 400 Bad Request：客户端请求参数非法、缺少必填字段或格式校验未通过。
- 401 Unauthorized：未提供有效身份凭证或登录令牌已过期。
- 403 Forbidden：已通过身份认证但无权操作该资源。
- 404 Not Found：请求的资源路径或特定实体数据不存在。
- 500 Internal Server Error：服务端未捕获的运行时异常或内部错误。

## 四、接口文档交付物与可验证性

智能体在确立接口契约后，必须执行落盘归档：

1. 存储路径与命名：接口文档统一归档保存在 docs/api 目录下，按业务模块划分文件，例如 docs/api/auth.md 与 docs/api/tasks.md。
2. 完整要素清单：每个接口详细说明必须包含接口功能概述、请求方法、完整路径、请求头要求、Query 参数、请求体样例、成功与典型错误响应体样例。
3. 必须提供真实 curl 调试样例：每个接口定义文末必须附带一个可直接在终端中复制运行的 curl 请求命令示例，方便开发者进行脱机验证。

---

## 五、阶段完成标准与流转

满足以下全部条件即视为完成本阶段：
1. 涉及的所有前后端交互点均已完成 RESTful 资源化路径与动词映射。
2. 统一成功与错误响应封套确立完毕，业务错误码体系清晰无冲突。
3. 接口规范已完整沉淀到 docs/api 目录下的独立文档中，包含可复制的 curl 测试样例。
4. 契约内容已与前端页面原型及后端架构充分对齐，并获得用户确认。

达成上述条件后，智能体输出接口定义摘要，正式流转至阶段 06 测试规范。

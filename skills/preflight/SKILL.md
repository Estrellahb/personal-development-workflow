# 前置检查与环境应急规范

> 本文件为项目开发工作流的阶段 00 规范。所有智能体接手任务后必须首先执行本检查，检查未通过前严禁编写业务代码。

---

## 一、阶段定位与执行门禁

1. 准入门禁：进入项目后优先读取本规范，核验运行环境、网络与必备配置。
2. 阻断原则：若基础依赖缺失或网络受阻且未获解决，智能体必须就地中断，严禁绕过检查直接进入需求与编码阶段。
3. 执行输出：完成检查后，输出简洁的环境基线报告，确认各项状态正常后方可流转至下一阶段。

---

## 二、基础宿主环境与通用工具探测

智能体接手任务时，聚焦探测不依赖具体业务架构的通用开发底座与质量防线，严禁在架构确立前盲目预设具体的编程语言与业务依赖包：

### 1. 版本控制与工程防线检查
- Git 基础状态与身份预检：确认 Git 工具可用；检测当前工作区是否处于 Git 版本控制之下；重点检查当前 Git 的 user.name 与 user.email 是否已完成有效配置，杜绝在后续提交阶段遭遇身份缺失拦截。
- 忽略规则防线核验：检查根目录是否存在标准的 gitignore 文件；严格核查是否已将本地环境变量文件、密钥凭据、构建临时产物、包管理器缓存以及操作系统临时文件加入忽略清单，杜绝敏感信息泄露与脏提交。
- 提交前钩子与规范探测：检查仓库是否已挂载 pre-commit 提交前钩子或启用了统一的 Git Hooks 机制；确保在后续代码提交流程中，自动执行代码格式化、静态分析与提交信息规范化校验，守住最前端的代码准入底线。

### 2. 跨平台基座与代码风格一致性
- 编辑器通用规范：检查根目录是否存在 editorconfig 文件；强制统一全项目采用 UTF-8 编码、统一采用 Unix 风格的 LF 换行符，防范跨平台协作导致的整文件换行符异常漂移。
- 配置模版防线：检查是否具备不包含真实敏感密钥的 env.example 占位文件，规范后续环境配置的接入标准。

### 3. 智能体检索与底层工具链就绪
- 代码高效探索工具：探测宿主机是否安装了 ripgrep 极速检索工具；确保智能体在后续任务中具备秒级全文搜索能力，避免低效遍历。
- 网络与数据调试工具：确认系统具备 curl 与 jq 基础命令行能力，保障网络连通测试与结构化数据处理顺利执行。
- 容器化基础设施：检测 Docker 守护进程运行状态，确保后续具备环境隔离与本地容器拉起能力。
- 原型工具联动扩展：检测当前环境是否已配置来自 https://stitch.withgoogle.com/settings 的 Stitch MCP 服务，为后续自动化生成原型奠定基础。
- 终端与操作权限：确认智能体具备执行基础开发命令、修改工程配置与新建必要目录的合法操作权限。

### 4. 项目生命周期自适应处理
- 存量项目场景：若当前工作区已存在既有的工程配置与代码结构，智能体被动识别并继承现有基线，严禁盲目破坏既有约定。
- 全新项目场景：严禁在当前阶段强行要求安装特定语言运行时；具体的编程语言、框架选型与业务依赖清单一律推迟至阶段 02 架构分析中正式裁定。

## 三、网络连通性与 Clash 代理处理

当智能体在拉取依赖包、拉取 Docker 镜像或访问 GitHub 遭遇超时与网络阻断时，必须严格执行以下两级处理程序：

### 1. 第一级：默认代理尝试
优先使用 Clash 本地默认端口进行网络代理请求：
- 本地代理地址：http://127.0.0.1:7890
- 智能体自动配置临时环境变量尝试建立连接，验证是否能够恢复网络通信。

### 2. 第二级：主动询问交互
若探测 7890 端口失败或网络依旧不可达：
- 严禁行为：严禁静默报错，严禁无限制发起死循环重试。
- 交互动作：智能体必须立刻暂停外网操作，向用户主动提问。
- 标准提问文案：检测到当前网络受阻且默认 7890 代理端口不可达，请提供您当前 Clash 或本地代理的具体端口号。
- 获取用户指定的端口后，重新注入环境变量并复测连通性。

## 四、基础设施镜像与无代理应急方案

当本地没有运行 Clash 代理或代理不可用时，必须按以下经过实机验证的链接与步骤实施无代理加速应急：

### 1. Docker 镜像源加速应急
遇到镜像拉取超时或失败，通过修改 Docker 守护进程配置文件换用国内加速源：
- 配置文件路径：/etc/docker/daemon.json
- 当前实测可用镜像源列表：
  - https://docker.1panel.live
  - https://docker.m.daocloud.io
  - https://dockerproxy.net
- 配置与生效步骤：
  1. 在 daemon.json 文件的 registry-mirrors 列表中填入上述加速地址。
  2. 执行系统命令重启 Docker 守护进程以应用新配置。
  3. 重新拉取目标镜像验证加速效果。

### 2. GitHub 访问与克隆应急
在无代理环境下遇到 GitHub 超时或连接重置，采用以下经过实测可用的前缀反代加速服务：
- 当前实测可用前缀代理源：
  - https://ghfast.top
  - https://ghproxy.net
  - https://gh-proxy.com
- 操作执行策略：
  1. 仓库克隆加速：在原 GitHub 仓库地址前拼接上述可用前缀，例如指定命令：git clone https://ghfast.top/https://github.com/用户名/仓库名.git
  2. 源码包与 Release 下载：在原始下载链接前拼接前缀代理源地址获取直连流量。
  3. SSH 备用端口应急：若 Git 默认 22 端口遭受拦截，在用户主目录下的 ssh 配置文件中添加配置，将 HostName 指向 ssh.github.com 并改走 443 端口通信。

## 五、阶段完成标准与流转

满足以下全部条件即视为通过本阶段：
1. 基础宿主环境、Git 身份凭证、忽略防线、editorconfig 规范以及 ripgrep 等工具链检测完毕且状态正常。
2. 外部网络通信畅通，已建立 Clash 代理或完成镜像加速应急配置。
3. 基础设施镜像与访问就绪，无遗留网络阻塞隐患。

完成上述检查后，智能体输出检查通过确认语句，正式流转至阶段 01 需求分析。
